## 0. A3 引擎更新口径（2026-09-27 深夜：pkg2 r12 树 + P1/P2/A3 补丁 + SM_COUNT=60）

| 项 | 旧树（2026-09-26） | A3 树（r12 + SM_COUNT=60） |

| decode（同任务，K=2） | 85.9 t/s | 86.0 t/s（中性） |

### 9.2 三个结论

**① 解码全面变快（+45% ~ +98%），长上下文更明显。** 同一批题目，新线解码 117-184 tok/s
（老线 76-94）；**32k 上下文解码 134.3 vs 69.7**——上下文越长优势越大。来源是两点叠加：
**DFlash2 投机（本线新能力）** + 引擎本身（该引擎在 4080S 上的同夹具读数也高于老线同族）。

**② 预填变慢 13% ~ 43%（短题面越明显），这是 KVMem 环的真实代价。** 引擎日志给出钱的去向：

```
throughput | prefill 1.57k tok/s (7,833 tok) | running 1 (prefill 1) | host 23.6% (1.2s)
kvmem_score: SELECT label=text_prefill_chunk … kept=512 skip=…   （每个预填块一行）
```

主机层搬运占预填墙钟的 **21-24%**（主机层是环线核心机制，老线没有）；每个预填块跑一遍
内容打分/选页；分块更小（新线显式 `--prefill-chunk 512`，老线引擎默认 1024）。
**换来的是什么**：设备池（54,784 tok）**小于**逻辑上下文（262,144 tok）仍能跑——
老线 112k 就到显存顶了。短题面（≤8k）上这笔代价最扎眼；题面越长差距越小（32k 时只差 13%）。

**③ 短提示 TTFT 变差（299 ms vs 126 ms）：固定开销 +~170 ms。** 新线在 67 token 的
微型请求上也稳定 ~315 ms（日志 `TTFT 315 ms | queue 14 ms`）⇒ 不是预填慢，是**每请求固定开销**
（环的窗口装配 + 主机层 + DFlash2 首轮 + 视觉媒体管线）。对"打字机式短问答"是退步；
对长任务/长输出反而更快（思考轮墙钟 1776 vs 3486 ms）。

**两代一致的两项是脚本怪癖不是引擎差异**：[7] 捞针 0/3 根因是该项思考默认开 + max_tokens 小，
推理吃满预算正文空（新线独立针测 44k 题面两轮全命中，见 §10）；[11] 全 400 是该项把
`reasoning_effort` 与 `enable_thinking=false` 同时发，引擎按设计拒（`conflicting_template_option`）。
