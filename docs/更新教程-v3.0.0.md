# 更新教程：v2.0.0 → v3.0.0（双线：老线 A3 + fusion KVMem 环线）

> 适用范围：任何从 v2.0.0（或更早）升级到 v3.0.0 的部署；也适用于全新克隆用户按本文完整搭建双线。
> 一句话：**老线一切不变**（原地升级无感）；本版新增一条实验引擎线（fusion KVMem 环线），
> 配 v3 容器制品，两条线同一张卡互斥切换。逐项差异见 [Fusion-KVMem-部署与运行.md](Fusion-KVMem-部署与运行.md)，
> 实测对照见 [性能实测.md](性能实测.md) §9。

## 2. 兼容矩阵（引擎 × 制品，硬校验、无混搭路径）

| 引擎 \ 制品 | v2 件（`models/artifacts-pq2.ninfer` 等） | v3 件（`models/fusion/` 三件） |
|---|---|---|
| **老线引擎**（A3，`vendor/ninfer-4090w-ternary-a3`） | ✅ 已验（v2.0.0 生产线） | ❌ 拒载：entry magic 第 8 字节不匹配（v3 件是 `03`，老树 reader 硬编码 `02`） |
| **fusion 引擎**（`vendor/ninfer-fusion-kvmem`） | ❌ 显式拒载：`NInfer v2 artifact is not supported. Upgrade to v3 with: tools/upgrade_ninfer_v2_to_v3.py` | ✅ 已验（2026-10-10 首跑 + 40 万字符超窗针测两轮 PASS） |

判定方式（不依赖试载）：容器魔数第 8 字节即代际——`xxd -l 8 <制品>` 看 `…0002` / `…0003`；
两代引擎各自只认自己那代（源码位置：老树 `src/artifact/reader.cpp` 的 `kMagic`；
fusion 树 `src/artifact/framing.h` 的 `kEntryMagic` + `reader.cpp:26-33` 的显式 v2 报错）。

**推论**：升级 ≠ 替换，是**并存**。"支持新旧模型"在物理上就是"两套引擎+两套制品各跑各的"，
脚本/容器/CI 都按线分流。客户端无感：两线模型 id 都是 `qwen3.8-27b`，接口同 OpenAI 兼容，只有端口/线在切换。

## 3. 升级路径 A：只更新代码（不启用新线，零风险）

```bash
# GitHub（或魔搭镜像，国内直连）
cd ninfer-bonsai-4070ti && git pull          # 魔搭: git -C <clone> pull 或 modelscope download 增量
# 老线照旧：
./scripts/start-ninfer.sh work               # 行为与 v2.0.0 完全一致
```

老线的引擎、制品、脚本、容器镜像都没动 —— 不下载 v3 模型、不编译 fusion 引擎也完全可用。
建议顺手跑一次 `./docker/fetch-model.sh`（校验老制品）与 `python3 scripts/perf_test.py` 确认基线。

## 4. 升级路径 B：启用 fusion 环线（宿主直跑）

**B-1 取 v3 制品（三件进 `models/fusion/`，文件名字节数见 Fusion 说明 §2）**

```bash
./docker/fetch-model.sh --ms-fusion        # 魔搭增量下载（约 22GB）；或 full|mtponly|ptq1 单件
./docker/fetch-model.sh                    # 校验：应逐件报 ✅ SHA256 匹配
```

**B-2 编译 fusion 引擎**（Linux 官方无预编译；依赖同老线：CUDA ≥12.8、ffmpeg 开发库、cmake ≥3.28）

```bash
cd vendor/ninfer-fusion-kvmem/src-tree/fusion-engine-src
export TMPDIR=$PWD/build-89/tmp && mkdir -p "$TMPDIR"
cmake -S . -B build-89 -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_CUDA_ARCHITECTURES=89 -DNINFER_BUILD_APPS=ON -DBUILD_TESTING=OFF
cmake --build build-89 -j6 --target ninfer ninfer-serve
# 判据: build-89/apps/ninfer-serve 存在（作者机：1050/1050 目标、871MB、sm_89 cubin、ldd -r 干净）
# 克隆用户若不想本地编译：用容器线（路径 C）或拉 GHCR 现成镜像
```

**B-3 切换与验收（两线同端口 8088，先停对方）**

```bash
./scripts/start-ninfer.sh stop work        # 停老线
./scripts/start-fusion.sh                  # 默认档 fusion（全量件；首次自适应测卡 10-50s）
# 必核三行（dtype=rk4v4-e8 / [ring] budgets 四元==pool / reuse host-backed: on）：
grep -E "capacity \| KV|\[ring\] budgets|reuse host-backed" ~/ninfer-logs/ninfer-fusion-fusion.log
# 两条验收（短问答 + 40 万字符超窗针测两轮，两轮都要命中针号）：
python3 scripts/fusion_accept_test.py
```

**B-4 切回老线**：`./scripts/start-fusion.sh stop && ./scripts/start-ninfer.sh work`。

## 7. 回滚（v3.0.0 → v2.0.0 行为）

v3.0.0 对老线零改动，回滚主要是"不用新线"：

```bash
./scripts/start-fusion.sh stop                 # 停环线
./scripts/start-ninfer.sh work                 # 老线照常
git checkout v2.0.0                            # 需要旧脚本/旧文档时（vendor 新增目录可留可删）
```

v3 模型（`models/fusion/`，22GB）不用了可直接删，与老线制品互不影响。

## 8. 常见问题

- **Q：能用 v3 模型跑老线 / 用 v2 模型跑新线吗？** 不能，硬校验（§2），也不支持就地升级三元件。
- **Q：老线要不要跟着换 v3 模型？** 不需要；v3 的价值在 fusion 引擎的能力（262k 逻辑上下文/主机层/DFlash2），
  文本塔权重与老件同源（回答质量同水平）。
- **Q：升级后端口/客户端要改吗？** 不用：两线都 8088（容器 8089），模型 id 同为 `qwen3.8-27b`。
- **Q：CI 构建多久？** 老线单腿约 25 分钟；fusion 腿目标数多（1050）用时更长。四腿并行跑。
- **Q：只想试 fusion 不想下 22GB？** 单件即可：`--ms-fusion full`（8.87 GiB，默认档）或 `mtponly`（7.13 GiB，窗口大一倍）。
